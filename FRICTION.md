[Aug 14] [micrograd — derivative definition] Stalled ~1h on the formula (d(c+h) − d(c))/h. Root causes, found only after many rounds of re-asking: (1) read d(c+h) as multiplication, not "evaluate d at c+h" — didn't know math function notation IS a function call; (2) letter collision — d used as both the output's name and in dd/dc notation, c as both the parameter slot and the variable. Unblocked by: concrete numbers first (e=2, c=3, h=0.001), then "def d(c): return c + e — now what's d(c+h)?" — programming framing landed instantly. Categories: prerequisite gap; repeated follow-up questions; AI gave too much detail before finding the actual gap.

[Aug 14] [micrograd — notebook ghost bug] draw_dot(L) crashed with 'float' has no _prev, but the class on screen was correct. Cause: stale kernel state — L was built by an older buggy version of the class; fixed the code, never rebuilt the object. Fixed by Restart + Run All. Category not in the protocol's list: state desync between what's on screen and what's in memory. A companion watching the session would have seen the class redefined after L was created and said so. (Also: this is the .ipynb tax — a .py run top-to-bottom can't desync from itself.)

[Aug 14] [micrograd — backward()] Hit the blank page and asked the AI for "boilerplate" for backward() — i.e., asked it to do the exercise. Caught only because the no-code rule was pre-committed in HYPOTHESIS.md. This is the protocol's own category: "people mainly want AI to finish the work rather than help them learn" — felt the pull firsthand. What I actually needed was the Python closure syntax (a prerequisite), not the algorithm.

[Aug 14] [micrograd — writing the closures] WORKAROUND FOUND: translating math to code was hard until I hand-wrote the name mapping (a = self, b = other, c = out) and drew the flow diagram on paper as a reference. Worked immediately. Why: the stall was juggling two naming systems in my head — externalizing the mapping freed working memory for the logic. Same root cause as the derivative-notation stall (representation collision). Companion implication: a tool could auto-generate and pin exactly this — "here's the mapping between the video's math symbols and your code's variable names" — the moment you start implementing something you just watched. Protocol categories: workaround created; small tool I naturally wished existed.

[Aug 14] [micrograd — closures] Wrote `out._backward = _backward()` (with parens) in all three ops — called the function at build time and stored its return (None). Crash surfaced later as TypeError: 'NoneType' object is not callable, at the CALL site, far from the bug's home at the STORE site. Concept gap: function-as-value vs function-call — "hand over the machine" vs "run the machine." Lesson: the traceback shows where it hurt, not where it happened.

[Aug 14] [micrograd — backward design] Called o._backward() once and expected the whole graph to fill. Missing mental model: each _backward pushes gradient exactly ONE step; something must schedule ALL of them in order (topological sort). The video's split between _backward (one gear) and backward() (the crank) wasn't obvious until I hit it. Resolved with hints, then wrote the topo sort myself.

[Aug 14] [micrograd — stale state, SECOND bite] Fixed = to += in the class cell, saved, tested a+a — still got 1.0 and concluded "it's not accumulating, there is no trade off." Wrong: never reran the class cell, kernel still held the old class. Same disease as the morning ghost bug, opposite direction (fresh code, stale objects vs fresh objects, stale code). TWICE IN ONE DAY = this is a recurring category: on-screen code vs in-memory state desync. A companion that diffs "cells edited since last executed" would have caught both instantly.

[Aug 14] [micrograd — __pow__ type slip] Wrote other.data in the closure two lines under my own assert declaring other is int/float. Would have crashed only at backward() time, deep in a future training loop — closure captured the bug and sat on it. Cousin of the naming-collision family: `other` is a Value in add/mul but a raw number in pow, same name, different species per method.

[Aug 15] [MLP — comprehension slots] Layer.__init__: wrote range(nin) where nout belonged — the "what to build" slot and the "how many times" slot of a comprehension were not separate concepts in my head. [Aug 15] [MLP — zip silently truncates] The mis-built network (3-neuron first layer feeding 4-weight neurons) ran WITHOUT ANY ERROR — zip quietly dropped the extra weight. [Aug 15] [prerequisite gaps surfaced by building] Had to stop and ask: what IS w·x+b (answer: y=mx+b in n dimensions, weights=how much each input matters, bias=baseline); what IS parameters() (the list of live knob references, not a count, not data — roles live in the forward pass, the update treats all knobs identically); what is n (the MLP instance). None of these blocked WATCHING the video — all of them blocked BUILDING. Building is the only reliable gap detector I've found.

[Aug 15] [THE BOUNDARY BUG, both directions in one day] (1) Loss: wrote (x.data - y)**2 — numerically correct float, but .data severed the graph; loss had no ancestry, backward impossible. (2) Update: wrote p += -step*p.grad — Value arithmetic built a NEW object and rebound the loop variable; real knob untouched, loss frozen constant for 20 iterations, no error. Same Value/.data boundary, crossed wrongly in both directions, both failures SILENT. Rule extracted: graph-land for anything needing gradients; .data-land only for reading results and nudging knobs. This is PyTorch's .item()/.detach() trap and the in-place-update trap, met in miniature.

[Aug 15] [relu capstone — implementing a new op took 3 structural drafts]
Draft 1: out = self (no new node — would CLOBBER self's own _backward from its parent op) + returned -out for negatives (accidentally implemented abs). Draft 2: early return of raw int 0 (coercion would sever the graph silently). Draft 3: early return of a proper Value but with no closure — ACCIDENTALLY CORRECT (missing backward coincides with relu's zero-gradient rule). Big lesson from draft 3: my numerical verifier would have PASSED lucky-but-wrong structure — tests catch wrong behavior, only review catches wrong reasoning. Final fix: branch the NUMBER (t = max(0, data)), never the control flow. Related trap caught: after flooring, t no longer carries the input's sign — closure must judge the regime by information that still exists (t == 0 works; would have passed gradient to dead neurons otherwise).

[Aug 15] [DISCOVERED: dying ReLU, both variants, empirically] Run 1: network dead on arrival — output neuron floored for all 4 inputs at init, all 41 grads exactly 0.0, loss frozen at exactly 4.0 (= four (0∓1)² errors). Run 2: born alive (loss 3.03), one big step (loss UP to 3.19 — first live sighting of learning-rate overshoot), then death at iteration 2, flat 4.0 forever. The zero gradient that causes the death also prevents the resurrection. Named the phenomenon BEFORE looking it up. Also learned why real nets don't put relu on the output layer.

[Aug 15] [flag relay — plumbing a config through 3 classes took 4 rounds] (1) tried to put the conditional in Layer (wrong altitude — decision belongs in MLP, mechanism in Neuron, middle just forwards); (2) autocomplete ambush: `from sympy.logic import false` instead of Python's False; (3) both Layer and MLP ACCEPTED the flag then never forwarded it — parameter accepted-but-unused should be a screaming tell; (4) off-by-one: i == len(nouts) instead of len(nouts)-1 — never True, silently all-relu, network died identically again. Then len(nouts - 1) — subtracting from a list. Diagnostic gold: THREE different root causes produced the IDENTICAL symptom (flat loss 4.0) — flat loss tells you nothing about why; you have to open the body.

[Aug 15] [CAPSTONE RESULT] relu-hidden + tanh-output MLP: loss 5.98 → 0.0165 in 40 steps — beats the all-tanh original (0.043) by ~3x. The architecture I was forced into by watching networks die is the one practitioners actually use, arrived at by necessity instead of convention.

[Aug 15] [makemore — seeded generator inside the loop] Sampler emitted the same index forever (0, 3, 3, 3, ...): I re-created torch.Generator().manual_seed(...) EVERY iteration. Concept gap: a seeded generator is a positioned STREAM of randomness — the seed sets the playhead; re-seeding rewinds to the same spot, so every "random" draw was the identical draw. Fix: create the generator once, outside the loop; each call then advances the stream. Reproducibility = same seed, same SEQUENCE — not same number.

[Aug 16] [requires_grad is a graph-BUILD-time decision — hit THREE times] (1) Set flags after the forward → 'element 0 does not require grad', loss permanently graphless, re-flagging can't rewrite history. [Aug 15] [keepdim / broadcasting — the longest concept fight of the sprint] Took ~6 rounds of explanation to land, and the ARC of what finally worked is the finding: (1) worked examples with tiny numbers — partial; (2) live-executed shape demos across 2D/3D/4D — partial; (3) "dims are bracket depth, dim 0 is down, dim 1 is across, don't map to x/y (matrices are (row,col) = (y,x), reversed)" — fixed the foundation, which was the ACTUAL missing prerequisite; (4) a quiz with committed answers — verified the foundation; (5) rules of thumb ("keepdim always", "sum meets its matrix on the same line") — REJECTED by me as hardcoding, correctly; (6) what actually landed: the derivation — say the math in English ("each element divided by its row's total"), derive what shape delivers that under broadcasting (varies with i, constant across j → standing column), then keepdim is just the shortest spelling of the derived shape, alongside unsqueeze/reshape. Companion implications: the real gap was TWO levels below the question asked (dims themselves, not keepdim); rules-of-thumb offered before derivations get rejected by learners who want to own the reasoning; the "explain simpler" loop terminated only when the explanation switched from rules to derivation.
