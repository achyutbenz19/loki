[Aug 15] [relu capstone — implementing a new op took 3 structural drafts]

[Aug 19] [GPT day — nn.Module and the constructor-vs-call wall] Bigram -> n_embd split -> position embeddings, all built. The concept fights, in order:
- (B,T,C) felt wrong because makemore always FLATTENED the context into one prediction per example. Here every position is its own training example, so 8 predictions per row. Same unrolling I printed myself in get_batch and still didn't connect to the logits shape.
- C collision AGAIN (family #2): C was the embedding TABLE in makemore, here it's a dimension SIZE. And in the bigram C happened to equal vocab_size because the embedding table was doing double duty as the output layer — that coincidence is what made "the embedding is the logits" feel true. Broke the moment lm_head arrived.
- nn.Module: I write forward, the parent's __call__ calls it. Inheriting is what buys __call__, .parameters() auto-registration, .eval()/.train(). My wavenet classes inherited from nothing so I had to write __call__ myself — same machine, different division of labor. super().__init__() is mandatory or registration doesn't exist yet.
- THE BIG ONE: constructor args vs call args. Kept reading nn.Linear(32, 16) as if 32 and 16 were data. They're SIZES — they fix the weight matrix shape at construction, before any batch exists. The data only arrives at key(x). Thought vocab_size was an input; it's only a size, and only in lm_head, because that's the one layer whose output must be one score per character.
- embedding output shape: output = idx.shape + row.shape. Fetching one row PER index and keeping the layout — find-and-replace over a container, every int swapped for its vector. Same as C[X] in makemore, needed re-deriving anyway.
- position table indexed by arange(T), not by the token ids. T not BLOCK_SIZE because generate's sequence is shorter/longer than max. Wrote position_embedding_table(x) first — would have crashed on any char id >= 8.
